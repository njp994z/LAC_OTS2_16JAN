One master orchestrator, no question. Here's why and how.

## Why a Single Master

The plant is one thermodynamic system. The compressor sets the flow for everything downstream. The furnace outlet composition IS the converter inlet. The HIP/CIP hot-side duties determine the cold-side reheat to Pass 4. PID controllers cross section boundaries — the jug valve controls Pass 1 inlet temp using WHB bypass gas that originated at the furnace outlet.

If you split into separate orchestrators per section, you'd have to pass boundary conditions between them, synchronize timing, and handle race conditions where one section updates before its upstream neighbor. You'd essentially be reimplementing the master orchestrator — but worse, because now you have distributed state.

The master orchestrator already solves the entire plant in one pass (~5 ms) and produces all 24 streams + 31 sensor tags. Each screen just subscribes to its slice.

## Architecture

```
┌──────────────────────────────────────────────────────────┐
│           MASTER ORCHESTRATOR  (runs @ 1 Hz)             │
│                                                          │
│  PlantInputs ──► solve() ──► { streams, sensor_tags,    │
│                                 kpp, alarms }            │
└────────────┬─────────────────────────────────────────────┘
             │  Single JSON blob pushed via WebSocket
             │
     ┌───────┼───────┬───────────┬────────────┬──────────┐
     ▼       ▼       ▼           ▼            ▼          ▼
  [Home]  [Comp]  [Furnace]  [Converter]  [Absorb]  [Steam]
  Screen  Screen   Screen     Screen       Screen    Screen
```

Each screen component just picks its tags out of the single state object:

```jsx
// ConverterScreen.jsx
const tags = useOrchestratorState();  // single global state from WebSocket

// This screen only renders these:
const pass1_in  = tags["1540-TI-4110"];
const pass1_out = tags["1540-TI-4111"];
const pass2_in  = tags["1540-TI-4120"];
// ... etc
```

## The View Filter

Each screen calls one function — no separate solve:

```python
def get_screen_data(screen_name: str, full_result: dict) -> dict:
    """Filter the master result to just what this screen needs."""
    mapping = SCREEN_MAP[screen_name]
    return {
        "streams": {
            str(sid): full_result["streams"][str(sid)]
            for sid in mapping["streams"]
            if str(sid) in full_result["streams"]
        },
        "tags": {
            tag: full_result["sensor_tags"].get(tag)
            for tag in mapping["tags"]
        },
        "alarms": [
            a for a in full_result["alarms"]
            if a["tag"] in mapping["tags"]  # only alarms relevant to this screen
        ],
        "kpp": full_result["kpp"],  # KPPs always available
    }
```

## Why Not Per-Screen Orchestrators

Three deal-breakers:

**Consistency** — if the furnace screen and converter screen each solve independently and disagree on Stream 5 composition, you get impossible physics. One master solve guarantees every screen sees the same plant state.

**Controller coupling** — the jug valve PID reads Pass 1 inlet temp (converter section) and adjusts WHB bypass (furnace section). A DCS-style cascade controller spans multiple "sections." With one orchestrator, this is trivial. With separate ones, you need inter-process communication.

**Performance** — one solve of 24 streams takes ~5 ms. Running 6 separate partial solves with boundary synchronization would be slower and more fragile, not faster.
